# PLAN.md — детальный flow подключения нового Telegram-канала «KONDRATYEV IN TRADING»

Этот проект — измерительный стенд для сигнальных Telegram-каналов на backtest-kit:
LLM (`gemma4:31b-cloud` через json-inference) парсит посты автора канала в структурированный
сигнал, стратегия исполняет его в бэктесте на минутных свечах, отчёты и mongo-коллекции
показывают, есть ли в сигналах эдж. Общий плейбук — в `CLAUDE.md`; готовые каналы-примеры —
`content/crypto_yoda_channel/` (формат «диапазон + 5 целей + стоп») и `content/vershinin_trader/`
(формат «вход/выход отдельными постами + картинки»).

Задача этого документа: пошагово, без пропусков, записать ВЕСЬ процесс подключения канала
«KONDRATYEV IN TRADING» — каждый shell-вызов, зачем он сделан и что вернул — чтобы более
простая модель (sonnet) могла повторить процесс для следующего канала, просто идя по шагам.

Правила процесса (из CLAUDE.md + правки владельца по ходу):
- ничего не выдумывать — каждое утверждение о постах/картинках/данных проверяется скриптом;
- **ВСЯ рабочая возня (временные скрипты, скачанные фото, копия session.txt) — в `./tmp`
  в корне проекта, НЕ в папках существующих стратегий**; в `content/<channel>/` кладутся
  только финальные артефакты (стратегия, промпты, assets, README);
- временные скрипты называются `*.tmp.mjs` и удаляются после;
- vision-правила в промпт — только после просмотра реальных фото;
- схема LLM и промпт проектируются под формат ЭТОГО канала;
- сначала тестовая стратегия (интервал 4h) для отладки промпта на месяце постов, потом прод (5m/15м);
- смена схемы/промпта/отбора постов = новое имя кеша.

## Шаг 1. Найти канал в списке диалогов

**Зачем:** канал закрытый или без username — стратегии нужен его числовой id. telegram-reader
не имеет функции поиска по диалогам, поэтому берём сырой клиент `getTelegram()` и листаем
`getDialogs`. Запуск из папки существующего канала — там уже есть `session.txt`.

**Команда** (временный скрипт `find-channel.tmp.mjs` в `content/crypto_yoda_channel/`):

```bash
cd content/crypto_yoda_channel && cat > find-channel.tmp.mjs <<'EOF'
process.chdir(new URL(".", import.meta.url).pathname);
import { getTelegram } from "telegram-reader";

const client = await getTelegram();
const dialogs = await client.getDialogs({ limit: 300 });
for (const d of dialogs) {
  const title = d.title ?? "";
  if (/kondrat/i.test(title)) {
    console.log(JSON.stringify({
      title,
      id: String(d.id),
      username: d.entity?.username ?? null,
      isChannel: d.isChannel,
      participants: d.entity?.participantsCount ?? null,
    }, null, 2));
  }
}
console.log("total dialogs scanned:", dialogs.length);
process.exit(0);
EOF
node find-channel.tmp.mjs 2>&1 | grep -v "resize begin"
```

**Вывод:**

```json
{
  "title": "KONDRATYEV IN TRADING",
  "id": "-1002199975612",
  "username": null,
  "isChannel": true,
  "participants": 4859
}
total dialogs scanned: 23
```

**Результат шага:** канал найден, закрытый (username = null), id для стратегии —
`"-1002199975612"`. Ссылки на посты будут строиться как `https://t.me/c/2199975612/<id>`
(отрезаем префикс `-100`). Временный скрипт удалён.

**Анализ формата (выводы для проектирования):**

1. Формат близок к vershinin_trader, НЕ к crypto_yoda: нет диапазона входа и сетки целей;
   вход «взял в работу» по рынку, закрытие — отдельным постом. Значит: **два LLM-пайплайна
   (open/close), событийный вход через `listenIdlePing` + `commitCreateSignal`, копируем
   каркас vershinin_trader**.
2. Тикеры голые, без `#`: BTC, ETH, ARB, SUI, ZEC, XRP → фильтр до LLM невозможен, промпт
   обязан требовать «просмотри ВСЕ сообщения».
3. **Направление часто отсутствует в тексте** («взял в работу», «переоткрыл») — оно на
   скриншоте. Картинки ОБЯЗАТЕЛЬНЫ в запросе к модели; перед написанием vision-правил —
   смотреть реальные фото (Шаг 4).
4. Цель в тексте бывает ($82400, $2556, $0,1550) — но одна, не сетка; стопы автор ставит
   и двигает постами. Для теста достаточно направления (вход moonbag + свой хард-стоп),
   как у vershinin.
5. Особые случаи для промпта open: два тикера одним постом (1825); «выставил лимитный
   ордер» (1821) — НЕ рыночный вход (для простой версии считаем не-входом); планы
   с «буду/если» — не вход. Для промпта close: «тейк забрали», «закрыл», «фиксируйте
   полностью», «ушла по стопу» = close; «стоп подтянул/перевёл», «добавил маржи»,
   «продолжаю держать» = hold; пост 1818 — close (по старой) И вход (по новой) в одном
   тексте: open-пайплайн должен уметь взять из него вход, close-пайплайн — закрытие.
6. Числа с запятой («$0,2050») — модели надо велеть возвращать числа с точкой.
7. Плечи автора безумны (стоп -78% в посте 1799) — как всегда, плечи НЕ берём.

Временный скрипт удалён после шага.

## Шаг 4. Скачать и посмотреть фото глазами (ОБЯЗАТЕЛЬНО до написания vision-правил)

**Зачем:** направление у этого канала часто есть только на картинке. Правило CLAUDE.md
(инцидент №1 из шапки): vision-правила в промпт пишутся ТОЛЬКО по реально просмотренным
фото, не по догадкам «там наверное стрелки».

**Команда** (из `./tmp`; выбраны посты разных типов: вход с целью в тексте 1840, вход без
направления в тексте 1835, вход с направлением в тексте 1822, «цели и стопы на скрине» 1828,
«переоткрыл в шорт» 1810, «тейк забрали» 1830):

```bash
cd tmp && cat > photos.tmp.mjs <<'EOF'
process.chdir(new URL(".", import.meta.url).pathname);
import { scrapePage } from "telegram-reader";
import { writeFile } from "fs/promises";
const messages = await scrapePage({
  channel: "-1002199975612",
  limit: 50, offset: 0,
  when: new Date("2027-01-01T00:00:00Z"),
});
for (const id of [1840, 1835, 1822, 1828, 1810, 1830]) {
  const m = messages.find((x) => x.id === id);
  if (!m?.photo) { console.log(id, "no photo"); continue; }
  await writeFile(`photo_${id}.tmp.jpg`, Buffer.from(m.photo, "base64"));
  console.log(id, "saved");
}
process.exit(0);
EOF
node photos.tmp.mjs 2>&1 | grep -v "resize begin"
# затем каждый photo_*.tmp.jpg открывается инструментом Read (модель видит картинку)
```

**Вывод:** `1840 saved ... 1830 saved` — и просмотр каждого файла. Что реально на картинках:

- **1840** («взял в работу... Цель $82400»): панель позиции биржи — `BTCUSDT`, бейдж
  **«Шорт»**, `Кросс 100x`, PnL красный −6.17%, цена входа 84376.1, «Позиция TP/SL:
  82400 / --». Направление словом; TP на панели совпадает с целью из текста.
- **1835** («взял в работу», направления в тексте НЕТ): та же панель — `BTCUSDT`, бейдж
  **«Лонг»**, PnL зелёный +11.97%, вход 83690.8, TP 86000. **Направление существует только
  на скрине.**
- **1810** («Переоткрыл в шорт», тикера в тексте НЕТ): панель с **ДВУМЯ позициями сразу** —
  `XRPUSDT Шорт 50x` и `BTCUSDT Шорт 100x`, у обеих TP в поле «Позиция TP/SL». Тикеры —
  только на скрине; одна картинка может нести несколько позиций.
- **1828** («пока такие мысли. Цели и стопы на скрине»): скриншот TradingView с зонами
  и нарисованным зигзагом-сценарием — это ПЛАН/аналитика, не факт входа.
- Панели знакомого вида: направление всегда написано СЛОВОМ «Лонг/Шорт» в бейдже;
  **цвет цифр PnL — это прибыль/убыток, НЕ направление** (1840: шорт с красным минусом;
  1835: лонг с зелёным плюсом — но бывает и шорт в зелёном плюсе).

**Выводы для промптов:** направление и тикер читать с панели позиции (слово в бейдже);
TP панели — цель; TradingView-скрин с зонами при тексте «мысли/план» = wait; фото-хвосты
альбомов без текста — не самостоятельные сигналы.

## Шаг 6. Написать prompt_open.mustache и prompt_close.mustache

**Зачем:** формат канала = «вход и выход отдельными постами, направление на скрине» —
это формат vershinin_trader, значит два LLM-пайплайна. Промпты пишутся по структуре
vershinin, но ВСЕ примеры и правила — из реальных постов ЭТОГО канала (шаги 3–4),
ничего выдуманного.

**Действие:** созданы файлы (не shell — инструмент записи файлов):

- `content/kondratyev_trading/prompt_open.mustache` — вход только как СОВЕРШЁННОЕ действие
  («взял в работу», «открыл», «переоткрыл»); планы «буду набирать/если/жду» — wait;
  «выставил лимитный ордер» — wait; направление с панели позиции (слово «Лонг/Шорт»
  в бейдже), мульти-позиции на одном скрине, цвет PnL ≠ направление; «просмотри ВСЕ
  сообщения» (тикеры голые, фильтра до LLM нет); числа с точкой. Примеры: 1822 (short
  текстом), 1835 (long только с фото), 1840 (short с фото при цели в тексте), 1810
  (мульти-скрин), 1791 (SUI) + блок не-входов.
- `content/kondratyev_trading/prompt_close.mustache` — close: «закрыл», «тейк забрали»,
  «фиксируйте полностью», «прикрыл», «ушла по стопу»; hold: перенос/установка стопа,
  «добавил маржи» (усреднение), «продолжаю держать», новые входы; особый случай 1818
  (закрытие старой И вход в новую в одном посте); «по битку» = BTC.

## Шаг 7. Регрессия промптов: assets/validate.mjs

**Зачем:** обязательный шаг CLAUDE.md — каждый тип сигнального и не-сигнального поста
прогоняется через ТОЧНЫЙ пайплайн стратегии (та же схема, тот же промпт, та же сборка
messages С КАРТИНКАМИ) на живой модели до стабильного ALL PASS. Скрипт остаётся в assets
как регрессия после любой правки промптов.

**Действие:** создан `content/kondratyev_trading/assets/validate.mjs` — копия vershinin-овского
с заменой канала, схем не касался (формат тот же: open `{id, symbol, position: long|short|wait,
reasoning}`, close `{id, symbol, action: hold|close, reasoning}`), 14 кейсов по реальным постам:
7 open (short текстом; long ТОЛЬКО с фото; short с фото при цели в тексте; тикер только на
мульти-скрине; план; лимитка; реклама) и 7 close (закрыл; тейк забрали; фиксируйте; перенос
стопа; усреднение; закрытие+вход в одном посте; держу).

**Команда (прогон 1):**

```bash
cd content/kondratyev_trading && node assets/validate.mjs 2>&1 | grep -v "resize begin"
```

**Вывод (прогон 1): 13 PASS, 1 FAIL:**

```
FAIL close/ARBUSDT posts=[1818] -> close id=1818 (ожидалось hold)
  reasoning: Трейдер сообщил, что «Шорт-позиции ушли по стопам»... не отменяет факт закрытия
```

## Шаг 12. Фикс close-пайплайна («закрытие устаревшим постом»)

**Зачем:** багокласс из Шага 11 — close-пост, вышедший ДО нашего входа, убивал свежую
позицию.

**Действие** (правка листенера `listenActivePing` в `content/kondratyev_trading/main.test.ts`
И в `content/vershinin_trader/main.strategy.ts` — каркас общий, баг был в обоих):

```ts
listenActivePing(async ({ symbol, when, data }) => {        // + data
  ...
  if (new Date(message.date).getTime() <= data.pendingAt) { // пост старше входа
    Log.info("... close", `...: close-пост ${signal.id} опубликован ДО открытия позиции — игнорирую`);
    return;
  }
```

`data.pendingAt` — момент открытия нашей позиции (ms); `new Date(message.date)` обязателен —
из кеша дата приходит строкой. Кеши НЕ переименованы: фильтр живёт в листенере, вход
LLM не менялся. Проверка: `npx tsc --noEmit --strict ...` по обоим файлам — exit 0.
