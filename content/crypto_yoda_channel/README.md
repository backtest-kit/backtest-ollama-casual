# Стратегия crypto_yoda_channel

LLM-стратегия для [backtest-kit](https://github.com/tripolskypetr/backtest-kit): читает Telegram-канал `crypto_yoda_channel` через `telegram-reader`, извлекает торговые сигналы моделью `gemma4:31b-cloud` (structured output через [json-inference](https://github.com/tripolskypetr/json-inference)) и сопровождает открытую позицию трейлингом по уровням тейк-профитов с безубытком.

## Файлы

| Файл | Назначение |
|---|---|
| `main.strategy.ts` | Стратегия: получение сигнала, вход, трейлинг уровней, безубыток |
| `prompt.mustache` | Промпт для LLM: правила преобразования поста в JSON |
| `session.txt` | MTProto-сессия Telegram (создаётся `require("telegram-reader").signIn()`) |
| `dump/` | Отчёты бэктеста и jsonl-логи |

## Как работает

### 1. Получение сигнала (`getSignal`)

На каждый тик стратегия (через `Cache.file`, бакет `crypto_yoda_entry_v2`, интервал 4 часа — один LLM-вызов на 4-часовое окно):

1. Скрейпит посты канала за последние 4 часа (`scrapeLookback`, без look-ahead: пост, опубликованный позже текущего момента бэктеста, не виден).
2. Фильтрует посты по тегу монеты: для `BTCUSDT` ищется `#BTC` в тексте.
3. Если постов нет — `{ entry: null }`, LLM не вызывается.
4. Иначе посты уходят в `generateObject` (ollama, tool-вызов `provide_answer`): модель обязана вернуть объект по схеме `TradingPositionFormat`. Грамматика tool-вызова гарантирует структуру, рекурсивная валидация json-inference с ретраями — типы полей.

Схема ответа модели:

| Поле | Тип | Смысл |
|---|---|---|
| `id` | number | ID поста-источника сигнала, `-1` если сигнала нет |
| `symbol` | string | Тикер, нормализованный к `*USDT` (`#BTC/USDT` → `BTCUSDT`) |
| `position` | `long \| short \| wait` | `wait` — в постах нет входа (отчёты фильтруются) |
| `entryRange` | `{ from, to }` | Диапазон входа из поста |
| `targets` | number[] | Пять целей, строго числа (`items: number`) |
| `stoploss` | number | Хард-стоп |
| `reasoning` | string | Обоснование модели (для отладки, попадает в `note` сигнала) |

### 2. Условия входа (`getSignal` стратегии)

Вход отклоняется (`return null`), если:

- сигнала нет или `position === "wait"`;
- последняя минутная свеча не пересекает диапазон входа (`high < min(entryRange)` или `low > max(entryRange)`) — цена не в зоне;
- нет третьей цели (`targets[2]`).

При входе:

- **тейк-профит** ставится на самую дальнюю цель: `max(targets)` для лонга, `min(targets)` для шорта;
- **стоп-лосс** — из поста;
- все цели кладутся в `payload.levels` — их читают листенеры сопровождения.

### 3. Трейлинг уровней (первый `listenActivePing`)

Идея — «level ratchet»: позиция едет до последней цели, но каждый взятый уровень становится полом.

- `getCurrentLevel` — сколько целей цена уже пересекла в свою сторону (для лонга `price >= level`, для шорта `price <= level`); номер уровня = счёт, с 1.
- Новый уровень взят → нотификация «Достигнут уровень N из 5» + запись в `LEVEL_STATE` (per-signal стейт backtest-kit, сбрасывается сам при закрытии сигнала).
- Уровни не взяты (`lastLevel === 0`) → рэтчет молчит, позиция живёт до стопа/безубытка; раз в 15 минут пишется лог стагнации.
- Откат за взятый уровень: считается `drift` — на сколько цена ушла за уровень в неблагоприятную сторону (благоприятная сторона всегда даёт 0). Закрытие (`commitClosePending`) только при `drift > шаг_сетки × LEVEL_DRIFT_RATIO` (0.3), где шаг — расстояние до соседней цели. Люфт адаптивен к плотности сетки: у PENGU шаги ~0.3–0.9%, у BTC — сотни долларов, допуск масштабируется сам.

### 4. Безубыток (второй `listenActivePing`)

Независимый листенер со своим per-signal стейтом `BREAKEVEN_STATE`:

- когда цена прошла ≥ 50% пути от входа до TP1 (`BREAKEVEN_TP1_PROGRESS`), вызывается штатный `commitBreakeven` — SL переносится в цену входа (фреймворк сам проверяет покрытие комиссий и проскальзывания);
- срабатывает один раз на сигнал; закрывает класс убытков «почти дошёл до TP1 и развернулся в стоп».

### 5. Константы

| Константа | Значение | Смысл |
|---|---|---|
| `LEVEL_DRIFT_RATIO` | 0.3 | Люфт рэтчета, доля шага сетки целей |
| `BREAKEVEN_TP1_PROGRESS` | 0.5 | Доля пути до TP1 для вооружения безубытка |
| `STAGNATION_LOG_INTERVAL_MINUTES` | 15 | Период логирования стагнации |
| `interval: "4h"` (Cache) | 4 часа | Частота LLM-запросов на символ |

## Логи (`Log`, jsonl)

| Топик | Уровень | Когда пишется |
|---|---|---|
| `crypto_yoda trailing level_up` | info | Взят новый уровень |
| `crypto_yoda trailing drift` | debug | Каждый пинг, пока цена за взятым уровнем (`driftRatio` — доля шага) |
| `crypto_yoda trailing close` | info | Срабатывание рэтчета |
| `crypto_yoda trailing stagnation` | debug | Раз в 15 мин на нулевом уровне: `minutesActive`, `progressToTp1`, `progressToStopLoss` |
| `crypto_yoda trailing breakeven` | info | Стоп перенесён в безубыток |

По этим логам подбираются пороги: распределение пережитых `driftRatio` против дрифтов на закрытии — для люфта; траектории `minutesActive → progressToTp1` против исходов — для правил стагнации.

## Формат постов канала

### Сигнал (вход в позицию)

```
СИГНАЛ #BTC/USDT

📛 Риск сигнала: 6/10

🔑 Открыть ЛОНГ в диапазоне $78600 - $79400 - 6% депозита, плечо X15

🍒 Цели:

🔘 Закрыть по $80300
🔘 Закрыть по $80900
🔘 Закрыть по $82000
🔘 Закрыть по $83200
🔘 Закрыть по $84500

❗️ СТОП ЛОСС: $77400
```

Из него модель извлекает: `position` (ЛОНГ/ШОРТ), `entryRange` (диапазон), пять `targets`, `stoploss`. Направление целей: у лонга вверх, у шорта вниз — поэтому дальняя цель для лонга `max`, для шорта `min`.

### Отчёт о результате (фильтруется, вход не создаёт)

```
#PENGU/USDT
Тейк-профит 1 ✅
Тейк-профит 2 ✅
Тейк-профит 3 ✅
Тейк-профит 4 ✅

Прибыль: 53.2296% 📈
Период: 1 день 10 часов ⏰
```

Такие посты проходят фильтр по `#COIN`, но модель возвращает `position: "wait"` (промпт явно требует фильтровать публикации о результатах) — стратегия отвечает `null`. Шаблоны постов произвольные, общий вид сохраняется; рекламные вставки и аналитика без тикера отсекаются фильтром содержимого ещё до LLM.

## Запуск

```bash
npm start -- --entry --backtest --cache   # бэктест (фрейм из modules/backtest.module.ts) с прогревом свечей
npm start -- --entry --live               # live-режим
```

Смена схемы ответа LLM требует смены имени кеша (`name` в `Cache.file`) — иначе подмешаются закешированные ответы старой формы.
