# Руководство: подключение нового Telegram-канала со стратегией

Проект: backtest-kit + telegram-reader + json-inference (ollama, модель `gemma4:31b-cloud`).

**У каждого канала свой формат руководства.** Не только «диапазон + 5 целей + стоп»: канал может давать одну цель, цели в процентах, только направление, сетку усреднений, сигналы картинкой-графиком. Поэтому под каждый канал проектируются свои: схема LLM, промпт, правила входа и сопровождение позиции — **из постов автора, ничего не выдумываем от себя**. Наша задача — точно распарсить его руководство и быстро исполнить.

`content/crypto_yoda_channel/` — **разобранный пример** для формата «диапазон входа + 5 целей + стоп». Всё, что ниже помечено «(пример crypto-yoda)», — специфика этого формата, не шаблон; универсальны только шаги процесса и инфраструктура.

## Универсальный вывод: скорость входа

**Важно быстро открыть позицию по руководству автора** — эдж живёт возле момента публикации. Поэтому прод любого канала: интервал кеша 5 минут, вход только по посту не старше 15 минут.

Выводы конкретно crypto-yoda (проверять заново на каждом новом канале, не переносить вслепую): его диапазон «от-до» формирует поддержку/сопротивление из лимитников опоздавших; эдж раскрывается на горизонте 12–24ч; гейт по цене вреден (моментум-сигналы в зону не возвращаются); из руководства берём направление/зону/цели/стоп, но НЕ плечи (X13–25 при стопе ~4.5% — слив) и не его манименеджмент.

## Структура папки канала

```
content/<channel_name>/
  main.strategy.ts   # прод: интервал 5m, свежесть поста ≤15 минут
  main.test.ts       # НАБОР СНИППЕТОВ ДЛЯ КОПИПАСТЫ + тестовый вариант (4h)
  prompt.mustache    # промпт LLM под формат постов ЭТОГО канала (или prompt_open/prompt_close при двух пайплайнах)
  session.txt        # MTProto-сессия (общая, можно скопировать из соседнего канала)
  README.md          # описание стратегии и формата постов
  assets/            # инструменты канала (см. ниже)
  dump/              # отчёты бэктеста
```

`assets/` — отладочные скрипты, которые пригодятся снова, оформленные с шапкой-инструкцией (у yoda и vershinin уже есть — копипастить оттуда, меняя канал):

- `read-posts.mjs` — чтение постов (последние N / пагинация / по id);
- `download-photos.mjs` — скачать фото постов в jpg, чтобы посмотреть глазами;
- `validate.mjs` — регрессия промпта: обязательные кейсы через точный пайплайн стратегии на живой модели, exit-код 1 при FAIL. **Гонять после каждой правки промпта или схемы**; кейсы привязаны к id постов — устаревшие id обновлять;
- `read-cache.mjs`, `event-study.mjs` (у yoda) — инспекция measure-items и event study, работают с любым бакетом.

`main.test.ts` — это библиотека сниппетов: там есть всё, что выпилено из прода за ненадобностью, но пригодится в новом канале — per-signal `State`, безубыток (`commitBreakeven` + `BREAKEVEN_STATE`), логирование `Log.info/debug` (level_up / drift / stagnation / close) для подбора порогов. **Копипастим оттуда, не пишем заново.**

## Создание session.txt (одноразовая авторизация)

`session.txt` — MTProto-сессия userbot-а; общая для аккаунта, готовый файл можно просто скопировать из папки соседнего канала. Если сессии ещё нет (новая машина / новый аккаунт / сессию отозвали):

1. **Предпочтение проекта: используем встроенные дефолтные `CC_TELEGRAM_API_ID` / `CC_TELEGRAM_API_HASH` из telegram-reader** — ничего не задаём, чтобы не засирать среду переменными. Свои `api_id`/`api_hash` с [my.telegram.org](https://my.telegram.org) (через `setConfig` или env) — только если дефолтные перестали работать. Порядок разрешения: `setConfig` → env → встроенные дефолты; текущие значения видно через `getConfig()`.

2. Из папки канала (`content/<channel>/` — файл сохранится в cwd) выполнить одноразовый вход (**запускает сам пользователь** — процесс интерактивный):

   ```bash
   node -e 'require("telegram-reader").signIn()'
   ```

   В консоли появится QR-код — отсканировать в Telegram (*Settings → Devices → Link Desktop Device*); при включённой 2FA спросит пароль. Сессия сохранится в `./session.txt` и дальше переиспользуется всеми вызовами без повторной авторизации.

3. Проверить: любой скрейп из шага 1 ниже должен отработать без ошибки `getTelegram failed: no session found`.

## Шаг 1. Читаем посты канала через telegram-reader

Любая новая стратегия начинается с отладки промпта, а отладка промпта — с чтения реальных постов.

Правила запуска отладочных скриптов:

- `telegram-reader` читает `./session.txt` из **текущей папки** — запускать из `content/<channel>/`.
- Обычный ESM-импорт: `import { scrapePage, scrapeLookback, scrapeDay } from "telegram-reader";`
- Временный скрипт кладём рядом (`debug.tmp.mjs`), после отладки удаляем.
- Вывод фильтруем от шума: `| grep -v "resize begin"`.

Что смотреть (API: `scrapePage` — постранично без окна, `scrapeDay` — календарный день, `scrapeLookback` — окно назад от `when` без look-ahead):

```js
// последние 50 постов канала — изучаем форматы
const messages = await scrapePage({
  channel: "<channel_name>",
  limit: 50,
  offset: 0,
  when: new Date("2027-01-01T00:00:00Z"),
});
for (const m of messages) {
  console.log(`=== id=${m.id} date=${m.date.toISOString()}`);
  console.log(m.content.slice(0, 400));
}
```

Главная задача шага — **понять формат руководства автора**: что именно он даёт в сигнале (диапазон или точку входа? сколько целей и в ценах или процентах? есть ли стоп? текстом или картинкой?), какие ещё типы постов бывают (отчёты о результате, реклама, аналитика без тикера) и какой у канала тег монеты (`#BTC`, `#PENGU/USDT`...) — по нему стратегия фильтрует посты до LLM. Схема, промпт и сопровождение позиции проектируются из ответов на эти вопросы. Пример crypto-yoda: сигнал = диапазон «от-до» + 5 целей + стоп; отчёты «Тейк-профит N ✅» фильтруются.

Частные случаи, встреченные на практике:

- **Канал без тега монеты** (vershinin: тикеры голые — «BTC», «1000PEPE»): фильтр постов до LLM невозможен, модели уходит всё окно. Тогда промпт ОБЯЗАН требовать: «просмотри ВСЕ сообщения; wait только если НИ В ОДНОМ нет входа по {{symbol}}» — без этого модель цепляется за последний пост пачки и теряет сигнал из соседнего (поймано валидацией как FAIL).
- **Закрытый канал**: `CHANNEL_NAME` — числовой id (`"-1002833393903"`), ссылки строятся как `https://t.me/c/${channel.slice(4)}/${id}`.
- **Автор сам ведёт позиции** («закрываю шорты» отдельным постом): сопровождение — второй LLM-пайплайн `close` (свои промпт, схема `hold|close`, кеш) на `listenActivePing` + `commitClosePending`; вход через `listenIdlePing` + `commitCreateSignal` c `Position.moonbag` и СВОИМ хард-стопом — автор стопов не публикует. Схема стратегии при этом пустая: `addStrategySchema({ strategyName })` без `getSignal`.

## Шаг 2. Пишем prompt.mustache и отлаживаем LLM инлайн

`prompt.mustache` — структура по образцу crypto-yoda (кто мы — «провожу аудит рекомендаций трейдера», что вернуть — только входы для тикера `{{symbol}}`, реальные примеры постов канала с явным «что фильтровать»), но **примеры и правила — из постов ЭТОГО канала**.

Схема ответа проектируется под формат канала (json-inference `FormatModel`). `TradingPositionFormat` из crypto-yoda — пример под «диапазон + 5 целей + стоп»; у канала с одной целью или процентами схема будет другой. Универсальные правила формата:

- формат плоский: `{ type: "object", required, properties }`; у массивов обязательно `items: { type: "number" }` (без items модель возвращает числа/строки как повезёт); вложенные объекты поддерживаются (`entryRange: { from, to }`);
- дефолтов в формате нет — «если сигнала нет, верни -1 / 0 / [] / wait» пишем в `description` полей;
- в схеме всегда нужны: выход «сигнала нет» (`position: wait`), `id` поста-источника, `reasoning` для отладки — остальные поля диктует формат канала;
- `enum` только у string (`position: long | short | wait`);
- json-inference добавляет в результат служебный `_context` — не пугаться;
- **json-inference — это и есть фикс сломанного structured output в ollama.** Параметр `format` у ollama для cloud-моделей не применяется: модель отвечает markdown-забором (```json ... ```) или массивом вместо объекта, и `JSON.parse` падает. json-inference решает это иначе — схема передаётся как параметры tool-вызова `provide_answer` (passthrough в декларацию инструмента), грамматика tool-вызова заставляет модель вернуть валидный объект, ответ валидируется рекурсивно и перезапрашивается при несоответствии. Поэтому LLM зовём **только** через `generateObject`/`generateText` из json-inference, напрямую `ollama.chat` с `format` — никогда.

Отладка — временный скрипт с точным пайплайном стратегии на реальных постах:

```js
const result = await generateObject(
  InferenceName.OllamaInference,
  {
    format: TradingPositionFormat,
    messages: [
      { role: "user", content: renderedPrompt },
      ...messages.map(({ id, channel, date, content }) => ({
        role: "user",
        content: str.newline(`ID ${id}`, "", content, "", `[${date.toISOString()}]: https://t.me/${channel}/${id}`),
      })),
    ],
  },
  "gemma4:31b-cloud",
);
```

Обязательные кейсы: **каждый тип сигнального поста канала** (все поля извлечены, числа числами, направление верное) и **каждый тип не-сигнального поста** (отчёты, реклама → `position: "wait"`). Прогнать все до стабильного результата, только потом идти дальше.

## Шаг 3. Тестовая стратегия (4 часа)

Копируем `main.test.ts` соседнего канала, меняем `CHANNEL_NAME`, подставляем свою схему из Шага 2 (промпт уже готов). Интервал `4h`, окно скрейпа 4 часа, имя кеша `<channel>_entry_v1`.

**Тест не будет прибыльным — он опаздывает со входом на часы.** Его задача другая: отладить промпт на практике за целый месяц постов (бэктест дёргает LLM по всем окнам), набрать `measure-items` в mongo и логи для анализа. Проверяем после прогона:

- `mongodb://localhost:27017/backtest-kit` → `measure-items`: все не-null ответы модели (`payload.data.entry`), смотрим руками — верные ли позиции/цены/id, нормализован ли symbol;
- `dump/report/backtest.jsonl` — opened/closed, `payload` стратегии сериализуется в события (у crypto-yoda там `levels`);
- ошибки `GET_SIGNAL_FN thrown` — чинить промпт/схему, менять имя кеша, перегонять.

## Шаг 4. Прод (5 минут / 15 минут свежести)

Из отлаженного теста делаем `main.strategy.ts`:

1. **Новое имя кеша** (`<channel>_entry_v2`, дальше v3...) — при любой смене схемы LLM или логики отбора постов имя меняется обязательно, иначе подмешаются старые закешированные ответы.
2. `Cache.file` интервал `"5m"`.
3. Окно скрейпа = свежесть: `limit: FRESH_WINDOW_MINUTES (15), dimension: "minute"` — старый пост не попадает в выборку, LLM не тратится.
4. Явный гейт свежести в стратегии: `when.getTime() - new Date(message.date).getTime() > FRESH_WINDOW_MINUTES * 60_000 → null`. **Обязательно `new Date(...)`**: `Cache.file` персистит JSON, при чтении из кеша `date` — строка, `.getTime()` на ней падает.
5. Правила входа и сопровождение — **под формат канала**, из сниппетов `main.test.ts` (State, безубыток, Log-телеметрия). Пример crypto-yoda (формат «диапазон + 5 целей + стоп»): гейт по цене не ставится (моментум-сигналы в зону не возвращаются); тейк — на дальнюю цель направленно (`long → Math.max(...targets)`, `short → Math.min(...targets)`); стоп — из поста; цели — в `payload.levels`; сопровождение — рэтчет уровней (`getCurrentLevel` / `getLevelStep` / `getLevelDrift`, люфт `LEVEL_DRIFT_RATIO = 0.3` доли шага сетки). У канала без сетки целей рэтчет неприменим — сопровождение проектируется от того, что даёт автор (одна цель → безубыток + тейк; только направление → тайм-выход по горизонту эджа из event study).

## Вход через listenIdlePing (событийная стратегия без getSignal)

Два способа открывать позиции:

1. **Классический** (crypto-yoda): `getSignal` в `addStrategySchema` — фреймворк сам опрашивает стратегию на каждом тике и открывает по возвращённому DTO.
2. **Событийный** (vershinin): схема пустая — `addStrategySchema({ strategyName })` без `getSignal`, а вход коммитится из листенера:

```ts
listenIdlePing(async ({ symbol, when, currentPrice }) => {   // тикает каждую минуту, ПОКА ПОЗИЦИИ НЕТ
  const { signal, message } = await getOpenSignal(symbol, when); // обязательно под Cache.file!
  if (!signal || (signal.position !== "long" && signal.position !== "short")) {
    return;
  }
  await commitCreateSignal(symbol, {
    id: `${signal.id}-${signal.symbol.toLowerCase()}`,  // уникальный id сигнала
    symbol: signal.symbol,
    ...Position.moonbag({
      position: signal.position,
      currentPrice,
      percentStopLoss: HARD_STOP_PERCENT,
    }),
    note: JSON.stringify({ signal, message: omit(message, "photo") }, null, 2),
  });
});
```

Как это работает:

- `commitCreateSignal(symbol, dto)` ставит DTO в очередь — **следующий тик** потребляет его вместо `params.getSignal`. `priceOpen` в DTO опущен → вход по рынку немедленно; указан → scheduled-сигнал (ждёт цену, лимитка). Вызов отклоняется, если по символу уже есть сигнал или отложенное действие.
- `Position.moonbag({ position, currentPrice, percentStopLoss })` — хелпер уровней: возвращает `{ position, priceTakeProfit, priceStopLoss }`, тейк фиксированный +50% от текущей цены (фактически «до отмены»), стоп — заданный процент; направление лонг/шорт инвертирует сам. Для кастомных TP/SL есть `Position.bracket`.
- LLM-вызов внутри листенера ОБЯЗАТЕЛЬНО оборачивать в `Cache.file` — `listenIdlePing` тикает каждую минуту на каждый символ, без кеша это минутный спам LLM и Telegram.
- Сопровождение симметрично: `listenActivePing` (тикает, пока позиция открыта) + `commitClosePending` / `commitBreakeven` / `commitPartial*`.

Когда какой способ: формат канала укладывается в «пост → готовый сигнал с уровнями» — классический `getSignal`; автор ведёт позиции постами (вход и выход — отдельные решения в разное время) — событийный с двумя пайплайнами.

## Запуск бэктеста

```bash
npm start -- --backtest --ui --entry ./content/crypto_yoda_channel/main.strategy.ts
```

или альтернатива — с прогревом свечей (скачает свечи бэктеста, чтобы работать быстрее):

```bash
npm start -- --backtest --ui --entry ./content/crypto_yoda_channel/main.strategy.ts --cache
```

Путь после `--entry` — файл стратегии, которую гоняем (тест или прод). Live-режим: `--live` вместо `--backtest`.

**Эту команду запускает сам пользователь** — как и логин в Telegram (`signIn()`). Claude бэктест не запускает: просит пользователя запустить и после завершения анализирует дамп/Mongo.

## Режимы запуска: loader.config.ts и modules/

`config/loader.config.ts` — точка входа CLI. Флаги: `--entry <файл стратегии>` (обязателен, без него выход), `--backtest` / `--live` / `--paper` (режим), `--cache` (прогрев свечей, только вместе с `--backtest`: качает `1m` по границам фрейма для всех символов). Как всё связывается:

- `SYMBOL_LIST` — захардкожен прямо в `loader.config.ts` (правится руками) и прокинут в `globalThis`; прогон запускается **отдельно по каждому символу** (`Backtest.background` / `Live.background` per-symbol) — поэтому каждая копия стратегии фильтрует посты под свой `{{symbol}}`, и LLM-кеш ключуется `SYMBOL_timestamp`.
- Лоадер берёт **первую** зарегистрированную схему из `listStrategySchema()` / `listExchangeSchema()` / `listFrameSchema()` — т.е. режим определяется тем, какой модуль подключён в прогоне, а не именами. В одном прогоне должен грузиться ровно один exchange-модуль.
- Фрейм обязателен только для `--backtest` и `--cache`; `Live.background` вызывается без `frameName`.
- Ветки `--live` и `--paper` в лоадере **идентичны** (обе зовут `Live.background`) — различие режимов живёт в том, какой модуль биржи подключён.

`modules/paper.module.ts` и `modules/backtest.module.ts` регистрируют биржу под одним именем `"ccxt-exchange"` (ccxt binance spot, публичный доступ без API-ключей) и почти совпадают. Различий два: в backtest-модуле дополнительно `getAggregatedTrades` (`publicGetAggTrades` Binance) и `addFrameSchema` (фрейм бэктеста); в paper-модуле их нет. Обе схемы содержат **только данные и форматирование** (`getCandles`, `getOrderBook` — в бэктесте кидает ошибку, `formatPrice`/`formatQuantity` возвращают строки) — методов исполнения ордеров нет ни в одной.

`live.module.ts` (реальная торговля) в проект намеренно не пишется с нуля — код биржи с исполнением ордеров и API-ключами пользователь копипастит из другого своего проекта. При вставке проверить стыковку: `exchangeName` (оставить `"ccxt-exchange"` или следить, что грузится один модуль), формат свечей `{ timestamp, open, high, low, close, volume }`, строки из `formatPrice`/`formatQuantity`.

## Структура дампа (`content/<channel>/dump/`)

Отчёты пересоздаются каждым прогоном. JSONL — одна строка = одно событие, общая форма: `{ reportName, data: {...}, symbol, strategyName, exchangeName, frameName, timestamp }`; вся аналитика в `data`.

```
dump/
  report/
    backtest.jsonl        # главный: тики жизненного цикла позиций
    strategy.jsonl        # commit-события управления (breakeven и т.п.)
    breakeven.jsonl       # переносы стопа в безубыток
    highest_profit.jsonl  # пики профита по позициям
    max_drawdown.jsonl    # максимальные просадки
    partial.jsonl         # частичные закрытия
    heat.jsonl            # тепловая карта по символам
    performance.jsonl     # замеры производительности (огромный, для профилирования)
  log/
    log.jsonl             # Log.* — при Log.useJsonl() и вызовах Log в коде
```

**backtest.jsonl** — `data.action`:

- `idle` — тик без позиции, только `currentPrice`; это 98% объёма файла (237MB → 23MB без них), для анализа сделок бесполезен;
- `opened` — вход: `signalId`, `position`, `priceOpen/priceTakeProfit/priceStopLoss` + их `original*`-копии, `payload` (наши `levels`), `note` (полный JSON с entry и постом-источником);
- `active` — поминутный снапшот позиции: + `pnl`, `percentTp/percentSl`, бегущие `peakProfit*`/`maxDrawdown*`; по стриму восстанавливается траектория (максимальный взятый уровень, момент переноса SL);
- `closed` — финал: `closeReason`, `duration`, итоговые `pnl`/`peakProfitPercentage`/`maxDrawdownPercentage`.

Атрибуция закрытия без доп. полей: `closeReason: "closed"` = наш `commitClosePending` (рэтчет); `stop_loss` при `priceStopLoss !== originalPriceStopLoss` = безубыток; `stop_loss` без сдвига = честный стоп канала.

**strategy.jsonl** — каждое commit-действие (`action: "breakeven"`...) с полным снапшотом позиции и новыми ценами. **breakeven.jsonl** — по строке на перенос SL. **highest_profit / max_drawdown** — агрегированные пики/просадки.

**log/log.jsonl** — строка: `{ type, timestamp (бэктест-время), createdAt (реальное), methodContext, executionContext {when, symbol, backtest}, topic, args: [payload] }`. Работаем с парой `topic` + `args[0]` — по ним подбирались пороги люфта и анализировалась стагнация. В проде Log-вызовов нет — вернуть копипастой из `main.test.ts` при необходимости.

Управление дампом — `config/setup.config.ts`: `Log.useJsonl()`, `Markdown.useDummy()`, `Dump.useMarkdown()`.

## Log.info / Log.debug — телеметрия для подбора порогов

`Log` из backtest-kit — глобальный логгер с подменяемым бэкендом. В проекте включён `Log.useJsonl()` (в `config/setup.config.ts`) — записи ложатся в `dump/log/log.jsonl`. Другие бэкенды: `useMemory` (дефолт, в памяти + `Log.getList()`), `usePersist`, `useDummy` (глушилка).

**Сигнатура**: `Log.info(topic, payload)` / `Log.debug(topic, payload)` / `Log.warn(...)`. `topic` — строка-канал (`"crypto_yoda trailing drift"`), payload — один плоский объект в `args[0]`.

**Контекст добавляется сам**: каждая запись автоматически обогащается `methodContext` (strategyName/exchangeName/frameName) и `executionContext` (`when` — бэктест-время, symbol, backtest) через async_hooks — внутри стратегии и листенеров ничего прокидывать не надо. `timestamp` записи = время тика бэктеста, `createdAt` = реальное время. Тем не менее ключевые поля (`signalId`, `symbol`, `position`, `when`) дублируем в payload — так анализ-скрипту не нужно лазить в контексты.

**Конвенция уровней** (выработана на crypto-yoda):

- `Log.info` — редкие события-переходы: взят уровень, рэтчет закрыл, стоп перенесён в безубыток;
- `Log.debug` — плотные потоки измерений, из которых потом строятся распределения: дрифт на каждом пинге (только при `drift > 0`, не безусловно), стагнация с троттлингом (`minutesActive % 15 === 0`).

**Правила payload**: плоский JSON, числа — сырыми (не форматированными строками), обязательно поле-отношение для будущего порога (`driftRatio = drift / step`, `progressToTp1`), плюс текущий лимит (`driftRatioLimit`) — чтобы в логе было видно, при каком пороге писалось.

**Зачем**: это данные для подбора порогов без перезапуска бэктеста. Паттерн анализа (node-скрипт по log.jsonl): распарсить строки → сгруппировать по `topic`, внутри по `signalId` → сравнить распределения. Пример с crypto-yoda: перцентили «пережитых» `driftRatio` (за которыми позже был level_up) против `driftRatio` на закрытиях дали потолок шума 0.186 и обоснование люфта; траектории `minutesActive → progressToTp1` против исходов из `backtest.jsonl` — правила стагнации. Готовые каналы с полными payload — копипастой из `main.test.ts`.

## Чтение свечей и LLM-кеша из MongoDB

База `mongodb://localhost:27017/backtest-kit` (`@backtest-kit/mongo`). Для анализа руками — `node -e` с mongoose (он уже в зависимостях):

```js
const mongoose = require("mongoose");
const conn = await mongoose.createConnection("mongodb://localhost:27017/backtest-kit").asPromise();
const db = conn.getClient().db("backtest-kit");
```

**LLM-кеш — коллекция `measure-items`** (сюда персистит `Cache.file`/`Cache.fn`):

- `bucket` — имя кеша + интервал: `"crypto_yoda_entry_v3_5m_0"`;
- `entryKey` — `"SYMBOL_timestamp"` (таймстемп тика, ms);
- `payload.data` — то, что вернула обёрнутая функция (у нас `{ entry, message }`; `entry: null` = пустое окно, LLM не звался).

```js
// какие кеши есть и сколько в них записей
await db.collection("measure-items").aggregate([
  { $group: { _id: "$bucket", count: { $sum: 1 } } },
]).toArray();

// все не-null ответы модели по конкретному кешу — проверка качества парсинга
const docs = await db.collection("measure-items")
  .find({ bucket: "crypto_yoda_entry_v3_5m_0", "payload.data.entry.position": { $in: ["long", "short"] } })
  .toArray();
```

Так сравниваются два кеша между собой (v1 против v2 по одинаковым `entryKey` — не изменилось ли поведение модели после смены схемы) и достаются сигналы для event study.

**Свечи — коллекция `candle-items`** (наполняется `--cache`-прогревом):

- поля: `symbol`, `interval` (`"1m"`), `timestamp` (ms, начало свечи), `open/high/low/close/volume`;
- цена в конкретный момент: `findOne({ symbol, interval: "1m", timestamp: ts })`;
- диапазон (для касаний зоны, пробоев, ходов после поста):

```js
const candles = await db.collection("candle-items")
  .find({ symbol, interval: "1m", timestamp: { $gte: t0, $lte: t0 + 1440 * 60_000 } })
  .sort({ timestamp: 1 }).toArray();
```

Паттерн event study «ход после поста»: сигналы из `measure-items` (направление + таймстемп из `entryKey`) → цена на тике и через горизонты 15м/1ч/4ч/12ч/24ч из `candle-items` → направленный ход `((p1 - p0) / p0) * 100 * (dir === "long" ? 1 : -1)`, hit-rate и средние по горизонтам. Пре-дрифт (что было ДО поста) — те же горизонты с минусом: отличает «автор постит по тренду» от «информация появляется в момент поста».

## Метод отладки: инлайн-скрипты вместо догадок

Всё в этом проекте отлаживается самостоятельно, без прогона всего бэктеста: одноразовый `node -e '...'` или временный файл `debug.tmp.mjs` рядом со стратегией (удалить после). Принцип один: **не гадать по коду, а воспроизвести кусок пайплайна на реальных данных**.

**Куда лезть и как:**

- **Telegram** — скрипт из `content/<channel>/` (там session.txt): `scrapePage` посмотреть последние посты, `scrapeDay` — конкретный день, `scrapeLookback` с `when` из бэктеста — воспроизвести ровно то окно, которое видела стратегия. Шум фильтровать `| grep -v "resize begin"`.
- **Mongo** — `node -e` с mongoose (раздел выше): состав кешей, не-null ответы модели, свечи для event study. Однострочник до результата, без сохранения скриптов.
- **LLM** — скопировать из стратегии точный вызов `generateObject` (тот же промпт через Mustache, та же схема, та же сборка messages с `ID`/датой/ссылкой) и прогнать на конкретном посте. Не упрощать пайплайн — баг может жить именно в сборке сообщения.

**Как это работало на практике (кейсы этого проекта):**

1. **Падение `JSON.parse` на "```json\n[]\n```"** — не чинилось вслепую: сначала `scrapeDay` нашёл единственный пост дня (отчёт о тейках), затем точный повтор вызова стратегии на этом посте воспроизвёл байт-в-байт тот же ответ модели. Диагноз (cloud-модель игнорирует ollama `format`) доказан, а не предположен.
2. **Строгая типизация items** — эксперимент A/B/C/D: один и тот же пост, четыре варианта схемы `targets` (без items / number / string / вложенный объект). Контраст B против C (типы элементов меняются вслед за схемой при том же промпте) — прямое доказательство, что схема доезжает до модели и применяется.
3. **Смена схемы без сдвига поведения** — после перехода на `entryRange` сравнение кешей v1/v2 в mongo по общим `entryKey`: вердикты и все числа совпали, различался только свободный `reasoning`. Вывод: модель не детерминирована, но числа копирует из поста стабильно.
4. **Event study** — сигналы из measure-items + свечи из candle-items: направленный ход после поста по горизонтам, пре-дрифт до поста, касание зоны входа и глубина пробоя. Так выяснилось, где живёт эдж (12–24ч), что зона «от-до» работает стеной лимитников, и что фильтр «цена в зоне» терял лучшие сигналы.

**Правила:** временные файлы называть `*.tmp.mjs` и удалять сразу после; в `node -e` с одинарными кавычками shell не пережёвывает апострофы в русском тексте — длинные скрипты с кавычками класть во временный файл; каждый вывод скрипта строить так, чтобы он отвечал на один конкретный вопрос (MATCH/DIFF, hit-rate, перцентили), а не вываливал сырые данные.

## Пороги и константы: не подгонять под месяц

Любая константа, подобранная по одному месяцу бэктеста, — подгонка (15–18 сделок ничего не доказывают). Порядок работы:

1. **Структурные правила важнее магических чисел.** Безубыток после полпути к TP1 закрывает класс убытков «почти дошёл и развернулся» без единого фитинга — его параметр привязан к геометрии сигнала. Стоп канала — честная цена мусорного сигнала, раньше него не выходим «по ощущению мёртвости».
2. **Числа — только из распределений процесса, не из исходов сделок.** Люфт рэтчета 0.3 оставлен консервативно: на августе потолок «шумовых» откатов был 0.186 (n=62), т.е. любой порог 0.2–0.3 не трогал живые позиции. Это распределение, а не подбор по PnL.
3. **Кандидат в константу обязан пережить walk-forward**: расширить фрейм на 4–6 месяцев (`modules/backtest.module.ts`, свечи докачает `--cache`), гонять через `Sweep` (сетка параметров) и `Walker` (оптимизация на окне N, проверка на N+1) из backtest-kit. A/B двух правил — две `strategyName` в одном прогоне.

## Каналы с картинками (vision)

У `ScraperMessage` есть поле `photo` — base64 JPEG-превью поста (800px). Если канал постит сигналы графиками, картинка отправляется модели через `images` в сообщении json-inference:

```js
{ role: "user", content: "текст поста", images: [message.photo] }
```

Работает и в `generateObject`, и в `generateText`; `gemma4:31b-cloud` графики читает (проверено на Glassnode-чартах и позициях TradingView/BYDFi).

Правила, выученные на vershinin:

- **Правила про картинки в промпт писать только по реально просмотренным примерам** — скачать фото (`assets/download-photos.mjs`) и посмотреть глазами, а не предполагать «там наверное стрелки». У каждого канала свои типы изображений (график с position tool, шер-карточка биржи, скриншот панели позиции).
- Классическая ловушка: **зелёный/красный цвет цифр P&L — это прибыль/убыток, а не направление** (шорт в плюсе — зелёный). Прописывать в промпте явно: направление — только по слову Лонг/Шорт или положению зон тейка/стопа относительно входа.
- Добавление картинок меняет вход модели → **новое имя кеша**.
- Фото тяжёлые (~50KB на пост): при широком окне следить за латентностью LLM; в `note` сигнала фото не класть (`omit(message, "photo")`).

## Технические заметки (грабли этого проекта)

- `State` из backtest-kit — per-signal, контекст собирает сам (и внутри `listenActivePing` тоже); `State.enable()` НЕ вызывать — `@backtest-kit/cli` делает это сам.
- Инстансные `state.getState()/setState()` предпочтительнее статических `_getState/_setState`.
- Причина закрытия вычисляется из отчёта без доп. полей: `closeReason: "closed"` = наш `commitClosePending` (рэтчет), `stop_loss` + сдвинутый SL (`priceStopLoss !== originalPriceStopLoss`) = безубыток, `stop_loss` без сдвига = честный стоп канала.
- Запуск — см. раздел «Запуск бэктеста»; команду запускает сам пользователь.
- Символы для торговли — `SYMBOL_LIST` в `config/loader.config.ts`; фрейм бэктеста — `modules/backtest.module.ts` (смена периода = новое имя фрейма).
- `json-inference` — от 1.1.0 и выше (там `items`, вложенные объекты в схеме, `images` в сообщениях, `generateText`).
- Модель не детерминирована (`reasoning` и язык гуляют между прогонами), но числовые поля копирует из поста стабильно — tool-грамматика жёстко держит структуру.
- **Флуд Telegram** (проверено спамом): gramjs с дефолтным `floodSleepThreshold=60` на `FLOOD_WAIT ≤60с` молча спит и ретраит (вызов просто медленный), на `>60с` бросает `FloodWaitError` (поле `seconds`), telegram-reader его не ловит → долетит как `GET_SIGNAL_FN thrown`. Наказание эскалирует (4с → 22с → ...). С telegram-reader 1.3.0 TTL-кеши убраны из ScraperService — каждый вызов идёт в сеть.
- **sharp теряет платформенный бинарь** после любого `npm install` (npm сносит optional deps) — telegram-reader падает с «Could not load the sharp module». Лечится: `npm install --include=optional sharp`.
